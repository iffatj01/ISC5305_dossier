HW1 — The AI contract, practiced once

Covers Modules 1–2 · thin homework · released in two parts · due Tue Sep. 8, 11:59 pm.

Released Due What it needs
Part A — the AI contract Thu Aug. 27 (Module 1, Lesson 1) Tue Sep. 8 Nothing beyond that lesson. Start immediately.
Part B — one rubric category Thu Sep. 3 (Module 2, Lesson 1) Tue Sep. 8 The class-design rubric, taught that morning.

Both parts are due at the same time, in one push. There is no separate Part A deadline — the staged release exists so you can start Part A twelve days early, not so you can hand it in early.

Part A is the larger half and you have twelve days for it. Do not save it for the weekend before the deadline — the point of this homework is the loop, and the loop takes more than one sitting.

You will need git before you can submit. The minimal-git handout is Thu Sep. 3 — six commands, and pushing is submitting. Until then, work in a local directory. Nothing is lost: you create the repo that day and commit what you already have.

The point of this homework

Module 1 showed you two genuine AI replies to one prompt: one that looked professional and did not compile, one that compiled and chose silently at every edge the prompt left unpinned. Neither was wrong so much as unpinned. This homework has you run that loop yourself, once, end to end — write a spec, get two proposals, critique them, and let tests decide — on a problem small enough that nothing hides.

You are expected to use AI heavily. You are graded on how you steer, constrain, test, and critique it, not on whether you wrote the code yourself.

Part A — the trapezoid kernel

Released Thu Aug. 27 · due Tue Sep. 8 · 75% of the marks.

A1. Write a prompt that is a spec

Module 1’s prompt was deliberately underspecified. Yours must not be. Write one prompt that pins, at minimum:

  • the exact signature you want, including how the callable is passed;
  • the behavior for n <= 0, for a > b, and for a == b;
  • the error policy — return a sentinel, throw, or something else, named explicitly;
  • what “correct” means — the property you would test, not a vague quality word.

This is the agentic_spec pattern: the demonstration — ▶ agentic_spec — is the worked answer, and its pinned arm is the standard your prompt is measured against. Save it as prompt.md.

A2. Collect two implementations

Send that prompt to an AI and keep the reply verbatim — byte-for-byte from the code fence, nothing edited, added, or removed. Then get a second, genuinely different implementation. Either is acceptable:

  • the same prompt sent to a different model, or
  • the same model asked for a materially different approach (a hand-written loop versus std::accumulate, say — the comparison Module 1 Lesson 2 runs).

Save them as impl_a.cpp and impl_b.cpp, each with a provenance header comment: model and version, date, any non-default settings, and which reply of how many this was. If you discarded four replies to keep two, say so — selection is part of the disclosure, exactly as the course kit discloses its own.

A3. Review both against the 5-part checklist

For each implementation, work the checklist from Module 1: spec alignment · correctness and edge cases · safety · style · testability.

Write REVIEW.md containing at least three real findings across the two implementations, each stated as:

  • the category it falls under,
  • the symptom — what looks wrong,
  • the evidence — the compiler diagnostic, the probe output, the failing test. A finding with no evidence is an opinion.

Rule zero still applies: the compiler is the first reviewer. If an implementation does not compile, that is finding number one and you say so plainly.

A4. Write the tests

Write 5–8 tests in tests.cpp. They must run and they must be able to fail — a main that prints numbers next to expected values in comments is a demonstration, not a test.

Two requirements carry most of the marks here:

  1. A clause-to-test table in REVIEW.md. Every edge you pinned in A1 gets a row: clause → the test that checks it. A clause with no test means you specified something you never verified.
  2. At least one test that distinguishes the two implementations — one that passes on one and fails on the other. Two happy-path tests that both pass tell you nothing about either. If your two implementations genuinely agree everywhere you can probe, say so in REVIEW.md and show the probes you tried; that is a finding too, and an honest one.

A5. The reflection

REFLECTION.md, two pages maximum. Not a summary of what you did — the interesting content is where the loop surprised you. What did you leave unpinned that you did not realize was unpinned until a test failed? What did the second implementation reveal that the first one hid?

Part B — one category, on your own class

Released Thu Sep. 3, after the class-design rubric · due Tue Sep. 8 · 25% of the marks.

Module 2 Lesson 1 gives you a four-category rubric — data hiding and invariants · construction and default state · ownership and lifetime · interface clarity — and scores a Vector1D with it. The full four-category exercise is the in-class lab, not homework.

For homework, pick one category and apply it to your own Vector1D:

  • write the class (AI-assisted is fine, and disclosed as always);
  • score it against your chosen category, citing the specific lines that earn the score;
  • name one concrete defect that category exposes, and fix it;
  • show the fix is real — a test that fails before and passes after.

PARTB.md, one page maximum. Say which category you chose in the first line.

How it is graded

By the homework rubric, the same one used for all six homeworks. Two notes specific to HW1:

  • The evidence gates stop at three. The ladder is compiles → runs → tests → sanitizer, but the sanitizer is Module 3 material. HW1 is graded on the first three gates only. Running a sanitizer anyway costs you nothing and teaches you something.
  • Part A is 75% of the marks, Part B is 25%. Part B is deliberately small; it exists so the class-design vocabulary is used once before HW2 leans on it hard.

Everything above is a floor, not a target. A submission that meets every requirement and shows no evidence of having thought about the problem is a C.
