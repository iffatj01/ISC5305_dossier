Custom STL-Compatible Types

Main Takeaway

A user-defined value type earns its place in the STL by satisfying the small contracts each facility asks for: operator<< to print, operator== plus a std::hash specialization to be an unordered_map key, operator< (or C++20 operator<=>) to be ordered and sortable, and a noexcept move so vector relocates it cheaply. Each is a compile-time promise — miss one and you get a hard error or a silent slow path, not a warning. And a bare single-argument constructor is an implicit conversion until you mark it explicit, so wrong values slip into the wrong overloads unnoticed.

#include <iostream>
class Money {
public:
    explicit Money(long cents) : cents_(cents) {}
    long cents() const { return cents_; }
private:
    long cents_;
};
int main() {
    Money lunch{1250};
    // Money has no operator<< — std::cout can't format it
    std::cout << "cost = " << lunch << "\n";
}

// a free operator<< teaches std::cout how to format a Money
std::ostream& operator<<(std::ostream& os, const Money& m) {
    os << "$" << m.cents() / 100 << "."
       << (m.cents() % 100 < 10 ? "0" : "")
       << m.cents() % 100;

Key Idea

A user type prints only if you teach std::cout how. A free operator<< taking (std::ostream&, const Money&) and returning the stream integrates your type with cout, logging, and everything else built on <<. Without it, std::cout << money is a compile error — the stream has no overload that matches your type, so nothing downstream can format it.

▸Key Idea

To key an unordered_map (or unordered_set) on your type the container needs two things: operator== to compare keys, and a std::hash<Money> specialization to bucket them. Supply neither and the instantiation is a hard compile error (libc++ says the specified hash does not meet the Hash requirements). Specialize std::hash to hash the underlying value and your type becomes a first-class key.

#include <iostream>
#include <unordered_map>
#include <string>
class Money {
public:
    explicit Money(long cents) : cents_(cents) {}
    long cents() const { return cents_; }
private:
    long cents_;
};
int main() {
    // no operator== and no std::hash<Money> — the container can't
    // compare or bucket the key, so this fails to compile
    std::unordered_map<Money, std::string> menu;
    menu[Money{150}] = "coffee";
    std::cout << "unreachable\n";
}

#include <iostream>
#include <unordered_map>
#include <string>
#include <functional>
class Money {
public:
    explicit Money(long cents) : cents_(cents) {}
    long cents() const { return cents_; }
    bool operator==(const Money& other) const {
        return cents_ == other.cents_;
    }
private:
    long cents_;
};
// specialize std::hash so unordered_map can bucket a Money
namespace std {
    template <>
    struct hash<Money> {
        std::size_t operator()(const Money& m) const noexcept {
            return std::hash<long>{}(m.cents());
        }
    };
}
int main() {
    std::unordered_map<Money, std::string> menu;
    menu[Money{150}] = "coffee";
    menu[Money{500}] = "lunch";
    std::cout << "$1.50 -> " << menu[Money{150}] << "\n";
    std::cout << "items = " << menu.size() << "\n";
    // walk the buckets so the diagram mirrors real g++ placement
    std::cout << "buckets = " << menu.bucket_count() << "\n";
    std::cout << "150 -> bucket " << menu.bucket(Money{150}) << "\n";
    std::cout << "500 -> bucket " << menu.bucket(Money{500}) << "\n";
    // both land in the same bucket — walk its chain in real order
    std::size_t b0 = menu.bucket(Money{150});
    std::cout << "bucket " << b0 << ":";
    for (auto it = menu.begin(b0); it != menu.end(b0); ++it)
        std::cout << " " << it->first.cents() << "->" << it->second;
    std::cout << "\n";
}

std::unordered_map is a hash table: it needs std::hash<Money> to turn a key into a bucket index (k % bucket_count), and operator== to tell keys apart within a bucket. Supply both and Money becomes a first-class key. libstdc++ starts with 2 buckets, and 150 and 500 are both even, so both land in bucket 0 — a collision — and share a short list (newest key, 500→lunch, is prepended ahead of 150→coffee). Lookup is average O(1); real tables grow the bucket count to keep such chains short.

▸Key Idea

Ordered containers (std::set, std::map) and std::sort need only operator< — define that one and sorting and set membership work. C++20's operator<=> with = default goes further: one line generates <, >, <=, and >= (and defaulting operator== alongside gives == and !=), so you stop hand-writing six near-identical functions and can't leave them mutually inconsistent.

#include <iostream>
#include <vector>
#include <set>
#include <algorithm>
class Money {
public:
    explicit Money(long cents) : cents_(cents) {}
    long cents() const { return cents_; }
    // one operator< is enough for std::sort and ordered containers
    bool operator<(const Money& other) const {
        return cents_ < other.cents_;
    }
private:
    long cents_;
};
int main() {
    std::vector<Money> v{Money{300}, Money{100}, Money{200}};
    std::sort(v.begin(), v.end());
    std::cout << "sorted:";
    for (const auto& m : v) std::cout << " " << m.cents();
    std::cout << "\n";
    std::set<Money> s{Money{500}, Money{200}, Money{500}};

std::set is a sorted collection of UNIQUE elements, and it decides both "which comes first" and "is this a duplicate" using only your operator<. Inserting 500, 200, 500 it holds { 200, 500 }: the second 500 is silently ignored (shown dimmed and struck through), because operator< reports it as neither less nor greater than the 500 already present. Key Idea

std::vector relocates its elements when it outgrows its buffer. It uses your move constructor for that relocation ONLY if the move is noexcept — otherwise, to preserve its strong exception guarantee, it falls back to copying every element. A move constructor that can throw silently costs you the performance you wrote it for; mark it noexcept and the vector moves instead of copies.

Key Idea

A single-argument constructor doubles as an implicit conversion: with Money(long), a bare 5 or 500 silently becomes a Money wherever one is expected — including as the argument to the wrong overload. Marking the constructor explicit turns those silent conversions into compile errors, so a Money is only ever built when you actually asked for one. Same main() both tabs: only the explicit keyword changes, and it flips the dangerous lines from compiling-quietly to caught-at-compile-time. Make explicit the default habit.
