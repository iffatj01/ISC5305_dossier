Directing a repair — fix the bugs, keep everything else

Main Takeaway

THE FOUR QUESTIONS THIS PAGE ANSWERS, IN NO FIXED ORDER: is the code bug-free — never assumed, only evidenced, and Example 1's shipped Grid looks like ordinary course code while carrying three defects at once; how do I check whether there are bugs — the instruments shown across these examples (the author's test battery, the memory checker, the allocation counter, or an AI asked to look) each with a measured limit, not an assumed one; when bugs are fixed, how can I be sure, and how do I know the tests themselves are not the flawed part — the battery adjudicates both repair arms in Examples 2-3, and a weak test set can go green over a real bug (see the test-gate page for that half of the question); how do I keep a found bug from recurring — the directed repair answers this structurally, RAII on the owned storage making the double-free and the leak impossible by construction rather than merely fixed once, with the battery staying on afterward as a regression suite. READING FOR TROUBLE, WITHOUT A TOOL: for the copy defect, an ownership audit — for every delete[], who else believes it owns this pointer? For the chained use-after-free, trace every site that replaces the owned array and ask what else still points into the old block. For the leak, the counting instrument the harness itself uses: count what is allocated against what is freed. None of this is a requirement to hand-hunt bugs before reaching for a tool. The ranked objectives, in order: first, realizing that bugs may be present at all — the skill nothing else substitutes for; second, understanding each error once it surfaces, including its subtleties; third, directing tools — sanitizers, counters, models — to find them; finding bugs unaided is not required. The memory checker used on this page's consoles is a verification instrument for the claims made here, not the skill being taught — working programmers debugged for decades without one. WHAT EXAMPLE 4 SHOWED: two small, uninstrumented programs, each run five times, prove a crash-free run means nothing on its own — one prints the exact same wrong numbers every run (repeatable is not the same as correct), the other prints different numbers every run (a bug that will not reproduce is still a bug). Asked to diagnose the second one from the symptom alone, both models named the real cause every time; the tiers separated one level down, in fabricated precision the weaker model added and the stronger one did not — measured, not assumed. BOUNDARIES: ag_testgate owns how strong or weak a test battery can be and what a weak one hides; ag_diff (a later module) owns reviewing a change presented as a diff, which this page deliberately does not render; class_structure and ownership own the general C++ rules about ownership and the rule of three/five that this page leans on without re-teaching; agentic_spec owns what-must-not-change clauses as a general spec-writing discipline — the directed prompt here is one worked instance of that idea, applied to a repair instead of a from-scratch request.

// Author battery for ag_repair (identical across all tabs and all rolls).
// Counts every allocation/deallocation, checks hard-coded analytic truths,
// and runs one stage per argv (copy|chain|leak|regression); no argv = all.
#include <cstddef>
#include <cstdio>
#include <cstdlib>
#include <cstring>
#include <new>

namespace counter {
std::size_t allocs = 0;
std::size_t frees = 0;
}

void* operator new(std::size_t sz) {
    ++counter::allocs;
    if (void* p = std::malloc(sz)) return p;
    throw std::bad_alloc();
}
void* operator new[](std::size_t sz) {
    ++counter::allocs;
    if (void* p = std::malloc(sz)) return p;
    throw std::bad_alloc();
}
void operator delete(void* p) noexcept { if (p) ++counter::frees; std::free(p); }
void operator delete[](void* p) noexcept { if (p) ++counter::frees; std::free(p); }
void operator delete(void* p, std::size_t) noexcept { if (p) ++counter::frees; std::free(p); }
void operator delete[](void* p, std::size_t) noexcept { if (p) ++counter::frees; std::free(p); }

// grid.cpp — 1-D finite-difference grid (course code)
#include <cstddef>

class Grid {
public:
    Grid(std::size_t n, double dx)
        : n_(n), dx_(dx), data_(new double[n]), interior_(data_ + 1) {}

    ~Grid() { delete[] data_; }

    std::size_t size() const { return n_; }
    double dx() const { return dx_; }
    double value(std::size_t i) const { return data_[i]; }

    // Sample f(x) at the grid points x = i * dx.
    void fill(double (*f)(double)) {
        for (std::size_t i = 0; i < n_; ++i) data_[i] = f(i * dx_);
    }

    // Double the resolution on the same span: n -> 2n - 1 points,
    // keeping the old values and linearly interpolating the new midpoints.
    void refine() {
        std::size_t new_n = 2 * n_ - 1;
        double* fine = new double[new_n];
        for (std::size_t i = 0; i < n_; ++i) fine[2 * i] = data_[i];
        for (std::size_t i = 0; i + 1 < n_; ++i)
            fine[2 * i + 1] = 0.5 * (data_[i] + data_[i + 1]);
        reallocate(fine, new_n);
        dx_ *= 0.5;
    }

    // Second difference at interior index i (1 <= i <= size()-2),
    // scaled by 1/dx^2. Copies the values into a workspace first.
    double second_diff_at(std::size_t i) const {
        double* scratch = new double[n_];
        for (std::size_t k = 0; k < n_; ++k) scratch[k] = data_[k];
        double centre = interior_[i - 1];
        double result = (scratch[i - 1] - 2.0 * centre + scratch[i + 1]) / (dx_ * dx_);
        return result;
    }

private:
    void reallocate(double* fresh, std::size_t new_n) {
        delete[] data_;
        data_ = fresh;
        n_ = new_n;
    }

    std::size_t n_;
    double dx_;
    double* data_;
    double* interior_;  // = data_ + 1, cached for stencil loops
};

namespace battery {

double fsq(double x) { return x * x; }

// Truth (written decimals, exact in binary): on x = i*0.25, f = x*x,
// (f[i-1] - 2 f[i] + f[i+1]) / 0.25^2 == 2 exactly.
int run_regression() {
    Grid g(5, 0.25);
    g.fill(fsq);
    double v = g.second_diff_at(2);
    bool ok = (v == 2.0);
    std::printf("%s regression: second_diff_at(2) == 2.0 before refine (got %.17g)\n",
                ok ? "PASS" : "FAIL", v);
    return ok ? 0 : 1;
}

int run_copy() {
#if defined(AGREP_NO_COPY)

#else

                ok ? "PASS" : "FAIL", v);
    return ok ? 0 : 1;
#endif
}

// Truth: after one refine (dx 0.25 -> 0.125), the interpolated midpoints halve
// the numerator and quarter dx^2, so second_diff_at(even interior 4) == 4.0 exactly.
int run_chain() {
    Grid g(5, 0.25);
    g.fill(fsq);
    g.refine();
    double v = g.second_diff_at(4);
    bool ok = (v == 4.0);
    std::printf("%s refine chain: second_diff_at(4) == 4.0 after refine (got %.17g)\n",
                ok ? "PASS" : "FAIL", v);
    return ok ? 0 : 1;
}

int run_leak() {
    std::size_t a0 = counter::allocs, f0 = counter::frees;
    {
        Grid g(6, 0.5);
        g.fill(fsq);
        for (int k = 0; k < 3; ++k) (void)g.second_diff_at(2);
    }
    std::size_t allocs = counter::allocs - a0;
    std::size_t frees = counter::frees - f0;
    std::size_t leaked = allocs - frees;
    std::printf("%s leak: allocs=%zu frees=%zu leaked=%zu\n",
                leaked == 0 ? "PASS" : "FAIL", allocs, frees, leaked);
    return leaked == 0 ? 0 : 1;
}

}  // namespace battery

int main(int argc, char** argv) {
    const char* stage = (argc > 1) ? argv[1] : "all";
    bool all = (0 == std::strcmp(stage, "all"));
    int rc = 0;
    if (all || 0 == std::strcmp(stage, "regression")) rc |= battery::run_regression();
    if (all || 0 == std::strcmp(stage, "copy"))       rc |= battery::run_copy();
    if (all || 0 == std::strcmp(stage, "chain"))      rc |= battery::run_chain();
    if (all || 0 == std::strcmp(stage, "leak"))       rc |= battery::run_leak();
    return rc;
}

Key Idea

This is what the model was given: exactly one file, and nothing else — no sanitizer report, no bug count, no hint that anything is wrong. Grid is author-written; its three defects (a shallow-copy double-free, a cached pointer left stale after refine(), and a leaked workspace in second_diff_at()) are deliberate, planted for this page. The console below runs the same author battery every tab on this page shares; against the unrepaired file it catches the first of the three defects and stops there — an aborting check cannot see past its own abort, which is why the harness also runs each defect as its own separate check (recorded in the harvest, not in this single console).

How to read the code windows ahead: starting with Example 2, everything between the BEGIN model output / END model output marker lines is the model's code, byte-for-byte as it replied (a build test enforces this) — Example 1 above carries no markers at all, since it is entirely author code. Everything outside the markers — the allocation counter above the class, the battery namespace and main below it — is author code too, identical in every tab of Examples 2 and 3. When a run hits a memory fault, the console shows the memory checker's report and nothing else — any lines the program printed before the fault are not part of what that console displays. Note: the reply below counts "four memory defects" because it also flags a move-semantics concern raised by its own unique_ptr rewrite — not a defect in the original file. The three defects this page tracks throughout are the ones planted in grid.cpp.

Looking at this code, I can identify four memory defects:

1. **Missing copy constructor/assignment**: Without them, copying a Grid creates two objects sharing the same `data_` pointer. When one is destroyed, the other has a dangling pointer (use-after-free + double-delete).

2. **Memory leak in `second_diff_at`**: The `scratch` buffer is allocated but never freed—every call leaks memory.

3. **Dangling `interior_` pointer after `refine`**: After `reallocate()` updates `data_`, the cached `interior_` pointer still references the freed memory.

4. **Move semantics broken**: If defaulted, move assignment won't update `interior_` to point to the new data.

The fix: use `std::unique_ptr<double[]>` for RAII, implement all special members to maintain the `interior_` invariant, and eliminate the unnecessary scratch buffer in `second_diff_at`.

When `cout << word` receives a `char*`, it treats it as a C-string and reads bytes sequentially until finding a zero byte. Since there's no terminator, it reads *past the array* into adjacent memory—potentially printing garbage characters until a zero byte appears by chance.

2. **`trail` is uninitialized**  
   The array `trail[4]` lives on the stack and is never initialized. It contains whatever garbage values happened to be in that stack memory. On each program run, different code paths, library calls, or OS scheduling may leave different values on the stack, so `trail` prints different numbers each time.

**Why it compiles:** C++ allows this—it's not a syntax error, just undefined behavior at runtime.

**Why it runs:** The OS doesn't prevent access to the stack; it just doesn't guarantee what's there.

**The fix:** Add a null terminator and initialize the array:
```cpp
char word[5] = {'G', 'r', 'i', 'd', '\0'};  // or: = "Grid"
long trail[4] = {};  // default-initialized to zeros
```

Two sources of **undefined behavior** explain the varying output:

### 1. `word[4]` has no null terminator

```cpp
char word[4] = {'G', 'r', 'i', 'd'};   // bytes only, no '\0'
std::cout << word << '\n';              // UB: reads past end of array
```

`std::cout << word` is equivalent to `printf("%s", word)` — it scans memory byte-by-byte looking for a `\0`. Since the 4-byte array has none, it keeps reading into whatever happens to follow on the stack. That surrounding data changes between runs (other function calls, local variables, etc.), so the printed "string" varies.

### 2. `trail[4]` is never initialized

```cpp
long trail[4];                          // indeterminate values → UB
for (long v : trail) std::cout << v << ' ';
```

Each element of `trail` holds whatever garbage was left on the stack from prior operations — previous function calls, other locals, or just random bits. That's why different numbers appear each run.

### Bottom line

Both issues are **undefined behavior** per the C++ standard. The compiler is not required to give consistent results across runs (or even within a single run). To fix it:
- Add `'\0'` to `word`, or use an array with proper size (`char word[] = "Grid\n"`).
- Initialize `trail`: e.g., `long trail[4]{};`.
