STL (Standard Template Library)

Main Takeaway

Every container in the STL exposes the same iterator-based interface over a different memory layout, so one set of algorithms works on all of them. Choosing a container is choosing a cost profile — vector for contiguous/O(1) index, list for no-relocation insert/erase, map for sorted order, unordered_map for average O(1) lookup. Mutating a container while iterating it, or indexing past its bounds, breaks that contract — usually silently.

▸Key Idea

vector, list, deque, and forward_list all iterate over the same five values but store them differently. vector is one contiguous block; list is a doubly-linked chain of separately-allocated nodes; deque is fixed-size blocks indexed by a map; forward_list is the minimal singly-linked chain — it trades size() and random access for the smallest possible per-node footprint. Memory layout decides the cost profile: vector indexes in O(1) but relocates on growth, list and forward_list never relocate but have no O(1) index, deque compromises between the two.

#include <iostream>
#include <vector>
int main() {
    // vector: one contiguous block, elements move on growth
    std::vector<int> v;
    for (int x : {5, 2, 9, 1, 7}) v.push_back(x);
    std::cout << "size = " << v.size() << "\n";
    std::cout << "elements:";
    for (int x : v) std::cout << " " << x;
    std::cout << "\n";
}

▸Key Idea

map keeps keys sorted internally as a balanced tree, so iterating it always visits keys in order — at the cost of O(log n) insert and lookup. unordered_map is a hash table: each key lands in a bucket by its hash (key % bucket_count), giving average O(1) lookup but no sorted order; when two keys share a bucket they chain in a short list — a collision. set is the map's cousin, storing unique keys only, still kept sorted.

#include <iostream>
#include <map>
#include <string>
int main() {
    // std::map is a balanced tree — keys come out sorted, whatever the insert order
    std::map<int, std::string> m;
    m[4] = "d";
    m[2] = "b";
    m[7] = "g";
    std::cout << "size = " << m.size() << "\n";
    for (const auto& [key, value] : m) {
        std::cout << key << " -> " << value << "\n";
    }
}

std::map is a balanced (red-black) tree keyed by the key, storing key → value. Inserted 4, 2, 7 in that order, in-order traversal (left → root → right) still visits 2 → 4 → 7 — sorted, unasked. That ordering is why iterating a map is always sorted, at the cost of O(log n) insert and lookup.

#include <iostream>
#include <unordered_map>
#include <string>
int main() {
    // Request 5 buckets so a collision is visible: hash(int) is the int itself,
    // so key k lands in bucket k % 5 — keys 2 and 7 both land in bucket 2.
    std::unordered_map<int, std::string> m(5);
    m[4] = "d";
    m[2] = "b";
    m[7] = "g";
    std::cout << "bucket_count = " << m.bucket_count() << "\n";
    for (int k : {4, 2, 7}) {
        std::cout << "key " << k << " -> bucket " << m.bucket(k) << "\n";
    }
    // walk each bucket; bucket 2 holds a two-element list — a collision chain
    for (std::size_t b = 0; b < m.bucket_count(); ++b) {
        std::cout << "[" << b << "]";
        for (auto it = m.begin(b); it != m.end(b); ++it) {
            std::cout << " " << it->first << "->" << it->second;
        }
        std::cout << "\n";
    }
}

std::unordered_map is a hash table: key k lands in bucket k % bucket_count. With bucket_count 5, keys 2 and 7 both hash to bucket 2 — a collision — so that bucket holds a short LIST (7 then 2; new keys are prepended). Lookup is average O(1); only colliding keys share a chain, and real tables grow the bucket count to keep chains short.

    s.insert(4);   // duplicate is silently ignored
    std::cout << "size = " << s.size() << "\n";

}

std::set is a sorted collection of UNIQUE elements — no hierarchy between them, just sorted order. Inserted 4, 2, 7, 4 it holds { 2, 4, 7 }: the duplicate 4 is silently ignored (shown dimmed and struck through). Internally it is the same balanced red-black tree as std::map; here we show the set abstraction. std::multiset is the cousin that keeps duplicates.

▸Key Idea

An index loop only works because vector supports operator[]; a list has no such thing. An iterator is the uniform cursor every container provides regardless of layout, so the same begin()/end()/++it pattern walks a vector, a list, or a map alike. Range-for is sugar over exactly that iterator pattern — three spellings, one underlying mechanism, one answer.

#include <iostream>
#include <vector>
int main() {
    std::vector<int> v = {5, 2, 9, 1, 7};
    // works only because vector supports operator[] — a list has no such thing
    int sum = 0;
    for (size_t i = 0; i < v.size(); ++i) sum += v[i];
    std::cout << "sum = " << sum << "\n";
}
✓ Compiled
Program output
sum = 24

The index i walks 0..4 and stops the instant i == v.size() (5). Index 5 is one past the last element: the loop compares against it but never reads it. This spelling only works because vector supports operator[].

#include <iostream>
#include <vector>
int main() {
    std::vector<int> v = {5, 2, 9, 1, 7};
    // begin()/end()/++it is the uniform cursor every container provides
    int sum = 0;
    for (auto it = v.begin(); it != v.end(); ++it) sum += *it;
    std::cout << "sum = " << sum << "\n";
}
✓ Compiled
Program output
sum = 24

begin() points at [0]; end() points one past [4]. The loop walks the half-open range [begin, end): it dereferences every cell up to but not including end(). end() is a sentinel — dereferencing it is undefined behavior. Every container spells begin()/end() the same way, whatever its layout.

#include <iostream>
#include <vector>
int main() {
    std::vector<int> v = {5, 2, 9, 1, 7};
    // range-for is sugar over the exact iterator loop above
    int sum = 0;
    for (int x : v) sum += x;
    std::cout << "sum = " << sum << "\n";
}
✓ Compiled
Program output
sum = 24

range-for is pure sugar: the compiler rewrites it into the iterator loop above, calling begin() and end() for you. Same half-open range [begin, end), same one-past-the-last bound — just spelled without the visible cursor.

#include <iostream>
#include <vector>
int main() {
    std::vector<int> v = {5, 2, 9, 1, 7};
    // hand-rolled sort: the reader must re-derive "this sorts" from the mechanics
    for (size_t i = 0; i < v.size(); ++i) {
        for (size_t j = 0; j + 1 < v.size() - i; ++j) {
            if (v[j] > v[j + 1]) std::swap(v[j], v[j + 1]);
        }
    }
    // hand-rolled search
    bool found = false;
    for (int x : v) {
        if (x == 9) { found = true; break; }
    }
    // hand-rolled sum
    int total = 0;
    for (int x : v) total += x;
    std::cout << "sorted:";
    for (int x : v) std::cout << " " << x;
    std::cout << "\n";
    std::cout << "found 9 = " << (found ? "yes" : "no") << "\n";
    std::cout << "total = " << total << "\n";
}

#include <iostream>
#include <vector>
#include <algorithm>
#include <numeric>
int main() {
    std::vector<int> v = {5, 2, 9, 1, 7};
    // named algorithms say intent directly: sort, find, accumulate
    std::sort(v.begin(), v.end());
    bool found = std::find(v.begin(), v.end(), 9) != v.end();
    int total = std::accumulate(v.begin(), v.end(), 0);
    std::cout << "sorted:";
    for (int x : v) std::cout << " " << x;
    std::cout << "\n";
    std::cout << "found 9 = " << (found ? "yes" : "no") << "\n";
    std::cout << "total = " << total << "\n";
}

Key Idea

Both versions below sort the same data, search for the same value, and sum it — the hand-rolled loops and the named algorithms compute identical answers. The difference is what the code says: std::sort, std::find, and std::accumulate state intent directly and are correct-by-construction, while a hand-rolled loop makes the reader re-derive the intent from the mechanics. Prefer the named algorithm.

▸Key Idea

size() is how many elements are in use; capacity() is how much storage is actually allocated. A vector that outgrows its capacity allocates a larger block and moves every existing element into it — visible below as capacity jumping ahead of size. reserve() allocates the final capacity up front, so every push_back that follows lands in already-owned memory: no reallocation, no moves. This relocation is also why iterators die on growth — see the next example.

#include <iostream>
#include <vector>
int main() {
    std::vector<int> v;
    // no reserve: capacity grows on demand and may relocate every element
    for (int i = 1; i <= 5; ++i) {
        v.push_back(i);
        std::cout << "size = " << v.size()
                   << ", capacity = " << v.capacity() << "\n";
        // GAUGE: size fills the capacity track; capacity() is the max,
        // so a doubling capacity reads as a doubling track (stripped
        // from the console, drives the fuel bar)
        std::cout << "GAUGE:size:" << v.size()
                   << "/" << v.capacity() << ":push #" << i << "\n";
    }
}

#include <iostream>
#include <vector>
int main() {
    std::vector<int> v;
    // reserve up front: capacity is fixed, no reallocation as we push
    v.reserve(5);
    // the track is the reserved capacity — full width and never grows,
    // so the bar only fills; no reallocation
    std::cout << "GAUGE:size:" << v.size()
               << "/" << v.capacity() << ":after reserve(5)\n";
    for (int i = 1; i <= 5; ++i) {
        v.push_back(i);
        std::cout << "size = " << v.size()
                   << ", capacity = " << v.capacity() << "\n";
        std::cout << "GAUGE:size:" << v.size()
                   << "/" << v.capacity() << ":push #" << i << "\n";
    }
}

▸Key Idea

vector::erase invalidates the erased iterator and every iterator after it — the elements behind it all shift down by one. The correct pattern reassigns it from erase's return value, which points at the element that slid into the erased slot. The mistake keeps incrementing the same (now-stale) iterator with the loop's ++it, so it skips checking the element that just shifted into that position — an even number survives that should have been removed.

#include <iostream>
#include <vector>
int main() {
    std::vector<int> v = {2, 4, 9, 1, 7, 3};
    // erase() returns an iterator to the element that slid into the erased slot
    for (auto it = v.begin(); it != v.end(); ) {
        if (*it % 2 == 0) it = v.erase(it);
        else ++it;
    }
    std::cout << "remaining:";
    for (int x : v) std::cout << " " << x;
    std::cout << "\n";
}
✓ Compiled
Program output
remaining: 9 1 7 3

erase() returns an iterator to the slot the survivor slid into, so it points AT the 4 — the even 4 is caught on the next pass. Result: 9 1 7 3.

▸Key Idea

operator[] trusts the index completely — no bounds check, so reading past size() is undefined behavior; AddressSanitizer catches it as a heap-buffer-overflow. .at() checks the index and throws std::out_of_range instead, which is catchable and recoverable — this is the same fail-loudly tradeoff that motivates exceptions in Module 7.

#include <iostream>
#include <vector>
int main() {
    std::vector<int> v = {5, 2, 9, 1, 7};
    // operator[] trusts the index — no bounds check, reading past
    // size() is undefined behavior
    std::cout << "value = " << v[10] << "\n";
}

operator[] just offsets the base pointer by 10 and dereferences — no check. Index 10 sits well past the last valid index 4, so it reads unowned memory; AddressSanitizer reports a heap-buffer-overflow.

#include <iostream>
#include <vector>
#include <stdexcept>
int main() {
    std::vector<int> v = {5, 2, 9, 1, 7};
    try {
        // .at() bounds-checks and throws instead of reading garbage
        std::cout << "value = " << v.at(10) << "\n";
    } catch (const std::out_of_range&) {
        std::cout << "caught std::out_of_range\n";
    }
}
